# scoop

Goal: suggest what's next and how to split it across the team. The decision belongs to the owner.

1. Inputs (interviews: `pm/state/interviews.json` themes matched to a roadmap item or request item go into that item's "why now" as "raised in N of M interviews"; unmatched themes raised in 2+ interviews go under "Candidates", not into a wave, until the owner decides; demand: `build-waves` weighs value by `pm/state/signals.json` — customers, or log2 of the request count — and writes "N requests (M customers, rising)" into the "why now"; `psst` refreshes that file when there are inputs): the last `peek` (`pm/state/status.json`), `psst` (`pm/state/lowhanging.json`, filtered by the owner in `lowhanging.filtered.json`), the matrix and the head-to-head count, `decisions.md`, demand signal if there is one (`pm/state/signals.json`), who-does-what on the team (`product.md`).
2. Measure size from history: `node <skill>/tools/measure-size.mjs pm --bulk pm/state/lowhanging.json --json pm/state/size.json`. For each psst item: S/M/L from similar past work, a range (p25–p75), confidence, and a suggested owner; effort already spent on the item's own ref is reported separately, and only doc-touching work (writing a spec) is compared to similar doc work. If confidence is "medium" or "low," open the similar items yourself and accept or drop them: word similarity doesn't know meaning. If an unrelated match is a permanent false positive (e.g. "client portal" shows up because it's mentioned on a different tab), stop seeing it: `node <skill>/tools/learn.mjs pm reject "<candidate ref/title fragment>" --context "<topic>" --type size --reason "<why it's unrelated>"`.
3. **Run `psst` first when its check is stale** (`pm/state/psst-final.json` older than `lowhanging.json`, or missing): `build-waves` reads the receipts and the refuter's verdicts — held items go to "waiting on the owner's decision", refuted ones to "outside", checked ones lead "Now". Without them it builds from the raw list and marks backend items "unchecked". Let the script build the waves: `node <skill>/tools/build-waves.mjs pm --json pm/state/waves.json --md pm/waves.md [--capacity <days>]`. The score is computed with an explicit formula (Value × Confidence / Effort, each component with its own source; the "widespread" ceiling and each size letter's default day count come from `sources.json`'s optional `threshold` object — the ceiling is `threshold.common`, the day counts are in `threshold.sizeDays`, keyed by S/M/L). The waves:
   - **Now:** only needs a screen, or the current backend is already enough.
   - **When the code lands:** in an open PR, or blocked on someone else's work.
   - **Needs backend:** widespread among rivals, no backend evidence.
   Plus: Open requests, Doc fix, Waiting on the owner's decision, Out (not doing).
   `--md` only writes between `pm/waves.md`'s `<!-- nosy:build-waves -->` markers; the hand-written part (position, risk, suggestion) is yours. Without `--capacity`, the script suggests a capacity from team size but doesn't apply it.
4. Read the script's list and correct it: do the top 5 make sense, is there a mismatch (if so, fix `sources.json`'s `refs`/`glossary`, and log it as a tool gap too). For each item: why now (rival, demand, ease), size, whose work (a suggestion, not an assignment), which item it's tied to.
5. Follow the scope rule; don't put something the owner said "haven't decided that yet" about onto the roadmap (the script sorts these into "Waiting on the owner's decision" on its own; sort out any that slip through yourself).
6. Update `pm/waves.md`'s hand-written part and the page's "Waves" section; give one suggestion in chat ("do this first, because").
