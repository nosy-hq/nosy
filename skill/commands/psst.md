# psst

> Read `pm/map.md` first if it exists (apps live / beta / retired, deliberately off, what's said outside on purpose, past audits). An owner line in it beats what the scripts infer; an app the map calls retired isn't "the product".

Goal: find cheap, valuable work with evidence. Runs first on start-up.

0. First, refresh the scans (signals 7-10 and the demand column read from these; `nosy psst` runs them all on its own):
   - **Demand:** if `pm/signal/` (or `sources.json` `signal.path`) has support/interview/survey exports, or the product has a GitHub issue repo: run `lowhanging.mjs` once, then `node <skill>/tools/collect-signals.mjs pm [--gh] --json pm/state/signals.json`, then `lowhanging.mjs` again. An item customers asked for gets a **"Asked for"** column (count, customers, trend), +1 value, and wins ties: "asked for + ready" ranks above "ready" alone. Without demand data the list says how to get it. Interview and call notes in `pm/signal/interviews/` also become themes (`interview-themes.mjs` → `pm/state/interviews.json`): how many interviews raised each, 1–2 masked quotes with file:line, matched to a matrix row, roadmap item or request item. A theme raised in several interviews that matches nothing we have is a **candidate**: mention the top one to the owner.
   - `node <skill>/tools/plan-gates.mjs pm --json pm/state/plan-gates.json` — are features shipped in the last 90 days behind a plan/subscription gate. If there's no billing trace in the code, it produces no signal ("no pricing" can be a decision). Inspired by BVP's "Startup Pricing Journey" (value shipped but never packaged). A commit scoped by an app/package name (`feat(web-frontend): ...`) doesn't sit unassigned: the area is derived from the touched files' own feature folder instead (`app_scope_commits`/`app_scope_recovered` report the split). "Gated" is either a word match or a **traced** one — the gate call followed to the route/screen it actually guards (same-line, a nearby route registration, or a Next.js route file's own path) — a broad gate like `ai_enabled` traces to the route it's wired on even when the word shares no stem with the feature area (`gateKind: "traced"` vs `"word"`; the trace path is in `traces`).
   - `node <skill>/tools/scan-metrics.mjs pm --json pm/state/metrics.json` — do the product's main steps (signup, activation, revenue, referral, churn) fire an analytics event in the code; if `sources.json` has `metrics.northStar: { name, pattern }`, the event feeding the North Star is checked too. It looks only at event names, not event data. Inspired by Speedinvest's "Startup Metrics" (AARRR, North Star).
1. `node <skill>/tools/lowhanging.mjs pm --json pm/state/lowhanging.json` (sources come from `pm/sources.json`; the JSON feeds the page's auto-section). Before it, `node <skill>/tools/pending-backend.mjs pm --json pm/state/pending.json` (signal 9; `nosy psst` runs it for you). The script reads ten signals (numbered as in `lowhanging.mjs`):
   - (1) backend fields unused on screen (`dropped.pattern`; `opportunity` separates "not built yet" from `knowingly` deliberate omissions)
   - (2) request items whose status is "served" but whose latest UI line doesn't say "done"
   - (3) items whose status may be stale (a related feat/fix commit in the last N days)
   - (4) matrix cells where "backend's ready," widespread among rivals, partial for us (reads both matrix shapes, via `read-matrix.mjs`; an acquired or shut-down rival doesn't count)
   - (5) issues opened at us (a security or bug report never enters the ranking — detected from GitHub labels, a CVE/GHSA id in the body, or the issue type field, not from words; `sources.json`'s `issue.labels.security` / `issue.labels.bug` override the default label names; excluded ones are counted in a single "Reported risks, not ranked" line instead — psst doesn't triage code)
   - (6) endpoint exists, no screen for it (reads `pm/state/inventory.json` if present; `inventory.mjs` isn't specific to any one product, it scans routes/OpenAPI in any product. If this file doesn't exist — `move-in`/`inventory.mjs` never ran — the signal is silently skipped, the script neither slows down nor errors)
   - (7) shipped but tied to no plan (`pm/state/plan-gates.json`): not a verdict, a question — "which package does this belong in, or should it stay open to everyone?" Mark a deliberately open one with `learn knowingly`.
   - (10) **on the team's own next list** (`pm/state/team-next.json`; `node <skill>/tools/team-next.mjs pm --json pm/state/team-next.json`, `nosy psst` runs it): the paragraphs of the team's working notes (`sources.json` → `next.path`, or found by structure: the markdown files most edited lately that cite real repo paths, not docs-site pages) that cite the code and were edited in the last 14 days. In blind test v7 this list predicted what shipped within 10 days better than anything Nosy computed. Still check each one: notes also record what was just finished.
   - (9) **screen built, waiting for the backend** (`pm/state/pending.json`) — the mirror of "backend ready, no screen", and often the cheaper one: the UI and copy are done, one endpoint or field ships it. Found structurally, never from UI words: a placeholder component the product uses for "not there yet" (`PendingBackend`, `ComingSoon`…; name the product's own in `sources.json` → `pending.markers` if it isn't found), an explicit API call whose path has no backend route (needs `inventory.json`), a screen importing mock/fixture data. Screens naming the same request (§28) are one item. **Before you list one, look at the backend yourself:** what exactly is missing (a field, a parameter, a whole endpoint), what already exists that it can reuse, file:line for both. That check is what turns "a screen is waiting" into "one day of backend work ships it". Size it from that, not from the default.
   - (8) a main step or the North Star isn't measured (`pm/state/metrics.json`). If the North Star isn't defined and move-in didn't already ask (it asks in its one question round; "not now" counts as asked), ask the owner once, never in the middle of move-in's first tour: which single number best shows the value delivered to the customer? Write the answer to `metrics.northStar`.
   References in our open PRs are marked "in a PR" and sink to the bottom; a reference in a matrix row's note also counts (including for signal 6, though since the inventory's endpoints usually carry no K/§/# reference, this discount mostly shows up in the other five signals).
2. Apply the owner's earlier feedback: `node <skill>/tools/learn.mjs pm apply pm/state/lowhanging.json` → `pm/state/lowhanging.filtered.json` (silenced items drop out, "deliberate" ones are counted separately, "important" ones are pinned to the top). The page's Today section, the opening whisper, and `scoop` read this file; `diff` reads the raw list. If there are demand-signal files (`pm/signal/` or `sources.json`'s `signal.path`): `node <skill>/tools/collect-signals.mjs pm [--gh] --json pm/state/signals.json` — maps support, interview and issue text to matrix rows, request items, decisions, and psst items (personal data masked); "demand + ready" rows are the strongest candidates.
   - **Pulling demand from connected tools (read-only):** if the owner has a support, chat, call or feedback connector attached (Intercom, Zendesk, HubSpot, Slack, Gong, Fireflies, Linear…), ask once which ones to read and how far back (default 30 days) — outside move-in's first tour, which doesn't stop to ask; there, skip this and mention it in the report. Use only the connector's list/search/read tools; never reply, tag, close or change anything there. Save each tool's raw response as returned to `pm/signal/<tool>-<YYYY-MM-DD>.json` (one file per tool per run; don't rewrite or summarize it), then run `collect-signals`. It reads these native shapes directly: nested records (`conversations`, `tickets`, `results`, `calls`, GraphQL `nodes`), HTML bodies, epoch dates, and it skips our own side's replies (admin, bot, internal speakers) and Slack join messages. The files stay in `pm/signal/` on the owner's machine; personal data is masked only in Nosy's output, so suggest adding `pm/signal/` to `.gitignore` if `pm/` is committed. No connector: ask for an export file instead.
3. **Receipts first**: `node <skill>/tools/psst-receipts.mjs pm --json pm/state/receipts.json` (`nosy psst` runs it and writes `pm/state/receipts.md`). For each of the top items it lays out the request item's own text, the decisions that name it (dated from git), whether the commits and branches it mentions are already merged or older than a decision, and which apps contain the code names it mentions. Blind re-run v5 was lost on exactly these: a branch recommended for merging that a later decision had overruled, "just data entry" for plans whose fields didn't exist, "one wire" for a change another app had no support for. Before an item goes on your list:
   - **Read its receipts and answer from them.** If the request text or the screen's own `need` names fields or parts that don't exist yet, it isn't "data entry" or "config": size the backend work those parts take.
   - **🔧 Already written locally**: the receipt lists a branch the integration branch lacks, or uncommitted edits in a worktree, that touches the item's files or whose commits carry the item's reference (matched from `nosy facts`, which `nosy psst` refreshes when it is more than 12 hours old). On the first run on a real product 3 of 5 items were already done on the owner's own unpushed branches. Such an item is **not new work**: don't list it as cheap work; say "already written on `<branch>` by <person>, <local only / pushed, no PR / in PR #n>" and what is left to do (usually: finish and open a PR). It goes under that line, not in the list. A **weak match** (a documentation file, a file four or more focused branches touch, or a big branch) is a lead, not a finding: open the diff of the most focused branch before deciding. The receipt lists the 3 most focused branches of each kind and counts the rest. Local branch names, authors and commit subjects stay on this machine (`pm/state/receipts.json` is never published). If the receipts say local branches were not checked, run `nosy facts` first.
   - **⛔ Held on purpose**: the code at the item's evidence carries a ref (#385, K178) or a decision names that file. The team parked it on purpose. Don't list it as cheap work; if you think it no longer applies, quote the line and say why, and put it under "held, worth asking the owner" instead. Blind re-run v6's only loss was a section built from fields whose own comment said "a screen decision, not a missing read (#385)".
   - **Ticketed**: a #N in that comment which is an issue in `pm/state/facts/github.json` is a ticket, not a parking sign. Open: it is tracked and ready, so list it normally and name the issue. Closed: check it was finished before you list it. A ref with no issue behind it (K178, a PR, no facts built) is still held.
   - **Never recommend merging a branch or commit** without its receipt: already merged means the work is elsewhere (find what's really left); ⚠ older than a decision means it may implement what the decision replaced, so read the decision and say so.
   - **A code name missing from an app the change has to reach** (e.g. the field is in the backend but not in the service that must use it) makes it a cross-app change: never "one wire", never size S.
   - **Say where the list stood**: if nothing on the script's list survived (empty, or all noise: vendored code, test scaffolding, one banner behind every "plan" item), open with that — "the list gave nothing usable here; these come from reading the code" — and log the noise as a tool gap. `psst-refute apply` counts it for you (items with no receipt).
   - Fewer, verified items beat five. Two items you checked end to end are a better answer than five with one wrong. Say what you dropped after checking and why, in one line.
   - **A field one layer carries and the next drops**. When an item is about a response, a refusal or a screen that lacks something the backend knows, name the two types and run `nosy fields <From> <To>` (or `node <skill>/tools/fields.mjs <repo> <From> <To>`): it lists what is carried, what is dropped and where, with file:line. A dropped field is a lead: most are dropped on purpose, so it goes on the list only if a screen needs it, and cite both lines.
   - **Then the refuter**. Write your draft (at most 5 items) to `pm/state/psst-draft.json` as `{ "items": [{ "id", "title", "claim", "size", "evidence": ["file:line"], "receipt": <its rank in receipts.json or null> }] }`, run `node <skill>/tools/psst-refute.mjs pack pm`, and hand `pm/state/refute-packet.md` to the **nosy-refuter** sub-agent (fresh context, read-only; it tries to break each item against the code the way a strict grader would). Save its JSON to `pm/state/refute.json` and run `node <skill>/tools/psst-refute.mjs apply pm`: refuted items drop, weakened ones take the refuter's fix, and the precision goes to `pm/state/refute-log.jsonl`. Answer the owner from `pm/state/psst-final.json`, and say in one line what was dropped and why. If fewer than two items stand, say so rather than padding the list.
4. Read the list and interpret it: write a one-sentence "why now" for the top 5; when an item has demand, say it in the sentence ("asked 7 times by 3 customers, rising"). Filter out the script's false positives and fix the patterns in `sources.json` (also log it as a tool gap). If the owner calls an item "noise," "deliberate," or "important," don't ask again: `node <skill>/tools/learn.mjs pm mute|knowingly|important "<title fragment or ref>" --reason "<owner's sentence>" [--duration <days>]`. If the same call repeats three times, `learn.mjs pm suggest` suggests a pattern for `sources.json`; writing it needs the owner's approval (`--apply`). The "widespread among rivals" ceiling isn't fixed: it's tuned with `sources.json`'s optional `threshold.common` (default 3).
5. Save to `pm/lowhanging/<date>.md`. The page's "Today" section refreshes on its own via `auto-section.mjs`; only "What can be done now" gets your own manual entry (why now, size).
6. Suggest the next command: usually `spill <top item>`.
