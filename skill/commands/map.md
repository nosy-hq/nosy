# map

Goal: one page, `pm/map.md`, that tells every command what the product is made of and what only the owner knows: which apps are live, beta-only or retired, what each screen is called and where its code is, what's deliberately off, where the outside claims differ from the inside, past audits, and the owner's words for things. Without it, answers contradict each other ("there's no team screen" in one answer, "team management exists" in the next), miss a beta-only feature, or re-count what an earlier audit already counted.

1. **Draft from evidence.** Read `pm/product.md`, `pm/decisions.md` or the decision source in `sources.json`, the README and docs, each app folder's own README or package name, deploy config (compose files, CI workflows, env examples) for what actually ships where, and the git log for folders nobody has touched in months. Fill `templates/map.md`. Every line is marked `(inferred: <file:line or commit>)`, or `(open)` if you can't tell. Never invent a status.
2. **Ask the owner, once, only what changes answers**, at most 4 questions (the asking tool takes four at a time; a fifth question is an error), with AskUserQuestion when available. Priorities: which apps are live vs beta vs retired, and whether one product runs as two versions (an old one serving customers, a new one being built: they get a row each under "Versions in flight", not one status); features that exist in beta but not production; claims said a certain way outside on purpose; anything deliberately off; the last audit's numbers. Write the answers as `(owner, <date>)`.
3. **Keep it true.** When a later answer finds the code disagreeing with the map, say so in that answer and add the line to "Open questions for the owner". Don't silently rewrite an owner line. When the owner corrects an answer ("actually it's live in beta"), add that correction here as an owner line: that's how a correction sticks. When the owner answers a question, rewrite every line of the map about the same thing, not just the answer line: the table row that inferred "switched off" becomes the owner's "in use in beta", and the answered question leaves the open list. An inferred row left standing next to an owner line that contradicts it is read first and repeated. CI deploy switches (a paused `*_DEPLOY_ENABLED`) say whether a job ships, not whether the thing exists or is used; never infer "switched off" from them alone.
4. The map is for the owner and the agents, not for publishing: `tea` never copies it to a page. `privacy-scan` it before sharing it anywhere.
