# atlas

Goal: answer "where next?" the way `canwe` answers "can we do this?" and `scoop` answers "in what order?". A list of candidate markets (countries, segments, verticals or channels) is researched on the same axes, checked a second time, and shown as a matrix. The owner chooses; the ranking is a suggestion and says what it rests on.

It is the market side of looking ahead. `canwe` is about one feature, `neighbors` about the ones next door. Don't use `atlas` for either.

0. **What counts as a candidate, and the axes.** Read `pm/product.md`, `pm/map.md` and `pm/decisions.md` first: the owner's scope rule ("domestic only", "no payments yet") and any "not going to <market>" decision come before any research. Ask once what kind of candidate this is (a country, a segment of buyers, a vertical, a sales channel); the default is a country. The **axes** come from the pack's section 9 ("Expansion axes and registries") when the product has a pack that fills it (`--legaltech`, or `Pack:` in `product.md`); otherwise propose six to nine axes with the owner (for example: how easy the data or supply is to get and its licence, market size and price level, how crowded it is, how close the rules are to ours, regulatory friction, a bridge from where we are, a place to be found, the cost of a first demand test). Write the agreed axes to `pm/atlas/axes.md` so every scout and every file uses the same names. Copy `templates/market.md` to `pm/atlas/_TEMPLATE.md` if the owner wants to edit it.
1. **Candidates.** The owner's list wins. If they have none, propose at most 6 with one line of reason and a source each, and research only the ones they confirm. A candidate whose `Owner decision:` in an earlier file is `no` is not proposed again, and is not re-litigated: if new evidence contradicts the decision, ask "this conflicts with your decision of <date>, which one wins?".
2. **Facts that can be counted without a model.** When the pack names a registry (a JSON list of sources by country, a directory, a dataset index), fetch it **once** (`curl`, public, read-only) to a file in the scratchpad or `pm/signal/`, then `node <skill>/tools/atlas-seed.mjs <file> [<country codes>] --json pm/state/atlas-seed.json` (or `nosy atlas seed <file> …`). It counts per country (sources, complete, blocked, open without a key, rows, the biggest sources, why the blocked ones are blocked) and flags rows that may repeat. It reads only that file and uses no network. Its numbers are the registry's own: they are leads for the scouts, never findings, and "complete" in a registry is a collection status, not a licence.
3. **Say what it will cost before any agent starts**, one line: "N candidates, about <tokens> each (one earlier run on a real product: eight country reports took about 2.2 million tokens, around 275,000 each, and about 130 tool calls per report, plus six regulation and case-study agents at about 350,000 each), research tool: <web | the owner's chosen>, the worst case is the free tools running out of budget half way". If an earlier atlas run in this repo is noted in `pm/log.md`, use its own figure instead and say so. Offer to start with the top 3 candidates and see. **Give every scout a call budget in its task text** (about 35 tool calls is enough for a first pass: one run with a cap of 35 found a segment's main numbers, and the same job uncapped on a country took about 130); a scout that runs out leaves an axis `snippet` or `judgment` and says so, which is better than a long run.
4. **One sub-agent per candidate** (`nosy-scout` in the plugin, **sonnet**, background; not a smaller model: the one run we have of a smaller model on this job produced no source-read score at all and wrote unsupported claims about the owner's own product, see `docs/EVALS.md`); agents don't spawn agents. Start them all in one message. Each writes only its own `pm/atlas/<slug>.md`. The scout's rules are in `agents/nosy-scout.md`; the ones you must hold the line on here:
   - **The fallback chain:** search to find → fetch to read → `curl` or the public API for JavaScript and raw data → say that a browser render or the owner is needed. A source the scout couldn't read is `unreadable` in the file; the report names every one, so the owner can open it themselves or say it is not worth it. **Nobody works around a bot wall** (403, reCAPTCHA, a login): not you, not the scout.
   - **Evidence grades:** `read`, `snippet`, `unreadable`, `terms-unread`, `judgment`. Only `read` counts in the ranking. "The terms page couldn't be read" is its own grade because "free to use" is the claim most likely to be wrong.
   - **A paid research tool** only when `sources.json` `research.tool` names it and `paidRequiresOwnerOk` is `true`. A search integration that runs out of credit makes the scout fall back to free tools and say so in the file; it never fails the round.
   - **No shared cache yet.** Scouts re-read pages other scouts read; a run's real cost is partly that. Say it when you report the cost, and note it as a tool gap in `pm/log.md`.
5. **Verify before anything is ranked.** For each report, start a **different** `nosy-scout` in verify mode (fresh context; a smaller model is allowed here because the job is narrow, re-reading named claims from a second source, but check the first one by hand; it re-derives every claim that feeds a `read` score from a second source and writes `## Verification`). Hunting for errors is the point: an earlier run on a real product had a "795 thousand open decisions" figure for a country whose API wasn't open to programs, a registry count that doubled one court's rows, and a regulation date that only a bulletin for a different rule supported. Each of those was caught by a second look and none by the first. A claim the verifier couldn't check stays out of the ranking.
6. **The matrix.** `node <skill>/tools/atlas-matrix.mjs pm --json pm/state/frontier.json` (or `nosy atlas`). It reads every `pm/atlas/*.md`, checks the tables (a `read` score without a url, the same url behind three or more axes, an undated or stale row, an unknown grade, an axis missing from one file), and ranks **only** candidates that are verified, not marked `no` by the owner, and have at least half of the axes read from a source. Everyone else is listed under "not ranked yet" with the reason. The score is the plain mean of the `read` scores; no weights, so the owner can see exactly where it came from. Exit 2 means the output has something to look at (stale rows, a problem, a candidate that couldn't be ranked).
7. **Say it the owner's way**: "Where next" in three lines: the top suggestion and the one thing it hangs on ("5 of 9 axes read from a source, verified 3 Oct"), what is not ranked and why, and the cheapest next step (a source to open by hand, a test to run). Then the owner's call: a "yes" or "no" goes into `pm/decisions.md` in their own words, and the file's `Owner decision:` line follows. Nosy assigns nobody to anything and never writes outside.

**Always:**
- **Not advice.** A regulation or legal note is research with a source and a date. Every report says so in "Risk", and so does the summary you give.
- **Licences are per source.** Before a registry's data goes into the owner's product, the licence of that source is read from its own terms, and the licence of the registry file itself (often unstated) is asked about. Say it when the owner proposes to copy a registry.
- **Dates.** A cell older than 90 days is stale (`--days` to change): rules, prices and rival lists move fast.
- **Dispatch without sub-agents:** if the agent can't start sub-agents, research the candidates yourself in sequence, at most 3 per session, and say the rest are "up next". Verify them with a fresh pass of your own, and say it was the same session.
- **Nothing here is built for Nosy Cloud yet.** A "Where next" view on the dashboard, a managed (budgeted, cached) research run and maintained registry data per vertical are separate work.
