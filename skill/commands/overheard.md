# overheard [hours=48] [--legaltech|--fintech|--mobile|--b2b-saas] [--diff [--fetch]]

Goal: as the team opens PRs quickly with coding agents, read ahead of the owner which decision each PR and issue serves. Not a code review: no comment on bugs, style, or test quality. The question is always a product question: is this PR on the roadmap, is it tied to a decision, does it touch one of the product's never rules, is it waiting on a pending decision?

For "which decision does this open PR serve," see `recent` (`node <skill>/tools/recent.mjs pm`): it answers that as a standing view — merged since the last run, plus open PRs close to merging (approved / green CI) — each tied to its decision/request/issue via `refs.mjs`, explicit refs only. `overheard`'s own job here (rules, CI, conflicts, staleness, per-PR detail) is unchanged; run both when you want the fuller preread.

1. `node <skill>/tools/preread.mjs pm <hours> [--<pack>] [--diff [--fetch]]`. A pack flag adds `packs/<pack>.md`'s "Patterns" list to the product's own `preread.never` rules; the pack's name then shows in parentheses in the rule column. Table order reflects that priority: tie and rule (product questions) first, CI and conflicts (context only) after. For each open PR: who, age, which decision/item/issue it's tied to, whether it trips a `preread.never` rule, CI, other PRs touching the same files, staleness, a reference not found in the decisions doc. Issues that moved and their latest comments.
2. Interpret: start with "3 things to look at." Priority goes to product questions: a PR not tied to a decision, a reference not in the decisions doc, a tripped never-rule, work not on the roadmap. CI and file conflicts are only context for "will this decision land this week" — not a finding on their own. `--diff` confirms a suspected rule violation (`gh pr diff N`); this usually fails on a 300+ file PR — if `--fetch` was also given, it fetches the branch (`git fetch origin pull/N/head:refs/nosy/pr-N`) and finds the line with `git grep`; otherwise it notes "couldn't get the diff, I can check with --fetch." Don't use `--fetch` on a read-only repo (e.g. the first product).
3. If the owner calls a rule trip "noise" or "known," make it stick: `node <skill>/tools/learn.mjs pm mute|knowingly "<ref or title fragment>" --type overheard --reason "<owner's sentence>"`.
4. The summary goes to the owner only. A comment, label, or approval on GitHub needs the owner's explicit request and a single approval card (what will be written, where).
