# neighbors

Goal: find each rival's current state and latest announcements, update the matrix.

**The rival registry comes first.** `sources.json` `rivals` holds each rival's pages by kind: `{ "<slug>": { "name", "site", "releases": [release notes / changelog], "news": [newsroom / press page], "blog": [blog], "login": [pages behind a login], "tier": "A" | "B" | "C", "stores": { "appStore": "<app id or apps.apple.com url>", "country": "tr" } } }`. `tier` says how hard to research it (A deep, the default · B watch only · C reference; see step 0); `stores.appStore` makes the sweep ask Apple's public lookup for the app's current version, date and release notes. Missing or thin: build it once from `pm/rivals/*.md` "## Sources" and one web search per rival ("<name> release notes", "<name> newsroom"); open each URL before writing it (the right domain: a rival on `.ai` is not on `.com`); ask the owner to confirm the list. Every command that reads rivals uses these addresses instead of guessing.

**"What did rivals put out in the last N days?"** (or any dated window). Always the same four steps, so two runs give the same list:
1. `node <skill>/tools/rival-sweep.mjs pm --days <N>` (`nosy sweep`): every registry page fetched, the dated entries inside the window listed with the page they came from, and the pages that couldn't be read (login, 404, JavaScript-only, no dates). It's a lead list, not a verdict. A rival with `stores.appStore` also gets Apple's lookup (`itunes.apple.com/lookup?id=…&country=…`, public, no key): the **current** version with its date and release notes, graded `primary`, labelled with that version. Those notes belong to that version only: never attach them to the version before it, and keep what a registry page says about an older version as that page's own entry. A failed lookup is a quiet "store lookup failed" in the unreadable list. A site that answers 429 is not asked again in the run ("rate limited, not read"). The **Chrome Web Store** has no stable public JSON API and is not scraped: an extension's version history is read from the page by the agent and graded `primary` only when the page shows the version and its date.
2. For each rival, one web search for press its own pages don't carry: `"<name>" <month> <year>` (funding, acquisitions, partnerships, a launch covered by the trade press), **in the rival's own market language too** when it isn't English (a Turkish rival's seed round is in Turkish tech press: `"Safahat" yatırım Eylül 2026`). Not optional: without it, funding and partnership news is missed every time.
3. Classify every item: **shipped** (on the release notes or changelog, or the page says available/GA), **announced** (newsroom, blog, press: beta, waitlist, "coming", a partnership with no date), **movement** (funding, hires, customers, offices). Release notes win when sources disagree.
4. Say which rivals had nothing readable and what you did instead. "Nothing new" only when the pages were read and the search came back empty.

0. Which rivals moved: `node <skill>/tools/watch-rivals.mjs pm --json pm/state/watch.json` (or `nosy watch`). It fetches each rival's public landing, changelog/release notes and pricing pages (picked from the file's "## Sources"; override per rival with `sources.json` `watch: { "<slug>": [urls] }`) and compares them with the last snapshot in `pm/history/watch/`. It masks numbers except on pricing pages and quotes the new sentences. It uses no model and reads public pages only. Then the plan: `node <skill>/tools/rival-tiers.mjs plan pm` (`nosy tiers`), which sorts the rivals by tier (`sources.json` `rivals.<slug>.tier`) and says who needs work now. **Research only the A-tier rivals it lists** (the watch says changed, or the file is older than 30 days; hand the agent the quoted new sentences as a lead, not as evidence). **B-tier rivals are only reported**: say what changed, research nothing. **C-tier rivals get a thin read** (3–5 pages, one pass) when due (file older than 90 days). Skip the rest and say so. A rival with no tier counts as A: ask the owner once and write the answer to `tier`. The plan's suggestions are suggestions, never a block: more than 10 A-tier rivals prints a line saying Nosy Cloud's scheduled watch is the better home for the surplus, and a B-tier rival that changed in 3 of the last 4 snapshots is offered for promotion ("promote to tier A?"): ask, never promote silently. "Not read" (JavaScript-only page, 404): add a readable URL to `watch` or research that rival by hand. The first run only saves the snapshot.
1. Read `pm/rivals/*.md`; get each one's "Latest major announcement" date. **No rival files yet** (move-in found none, or the owner picked none): find candidates with the built-in web search the same way move-in step 1 does (category, "alternatives to" / "vs" pages, products the repo names), show up to 4 with a one-line reason and source, and research only the ones the owner confirms. In a first tour with no one to confirm, research the top 3 and label them "(proposed, not confirmed by the owner)" in the rival file and in the report.
   **Before any agent starts, say what it will cost.** One line: "N rivals, about <tokens> each (one earlier run on a real product: about 98,000 tokens per rival, 11 rivals about 1.08 million), which of them `watch-rivals` says changed, and whether to research only those first." Take the per-rival figure from the plan (`sources.json` `tour.tokensPerRival` when the owner set it, else the 98,000 from that one earlier run, said as such); the plan already counts only the A-tier rivals that need work, plus the C-tier thin reads. Rivals the watch step reports as unchanged are not researched unless the owner asks. A rival the owner marked as a reference only (a concept, a law firm, not a product) gets a thin read of three to five pages, not a full pass.
2. **One sub-agent per rival the plan sent** (`nosy-neighbor` in the plugin, sonnet, in the background); agents don't spawn other agents (nested dispatch hits the concurrency limit). Start them all in a single message. Agent instructions:
   - **Research tool is configurable.** `sources.json` `research: { tool, fallback, paidRequiresOwnerOk }` picks the source tool: `tool` is `"web"` (default, WebSearch/WebFetch), `"firecrawl"`, or an MCP tool name. A paid tool (`firecrawl` or any non-`"web"` tool) is only used when `paidRequiresOwnerOk` is also `true` — the owner's explicit allow, not a default. No `research` key at all → free WebSearch/WebFetch, same as before. If the configured tool fails (credits, rate limit, outage), fall back to `fallback` (default `"web"`) and note the fallback in the rival file's "## Sources" line for that read (e.g. "· fell back to web: firecrawl credits exhausted").
   - Free tools only unless the owner explicitly allowed a paid one via `research.paidRequiresOwnerOk`. A paid tool (Firecrawl etc.) is never called just because it's installed, and never as a fallback when the free one fails; say it failed.
   - **No `research` in `sources.json` yet:** move-in normally asks this in its question round (step 1). If it's still missing (an older pm/), ask the owner once: "Web search for rival research: the agent's built-in search (free, default), or a search integration you've set up (name it; it uses that tool's credits)?" Write the answer to `research`. Don't ask again.
   - **Primary sources win:** a rival's own release notes / changelog page beats its newsletter, blog recap, press coverage or an aggregator. When they disagree (a newsletter says "coming soon", the release notes say "released 16 Sep"), the release notes are right. Cite the release-notes URL for anything you call shipped; if you only have a newsletter or snippet, mark it "(from a newsletter, not the release notes)".
   - Write only to your own rival file; don't touch any other file or git.
   - Primary sources first: the product's own changelog, blog/newsroom, pricing page, docs. Then press and community (G2, Reddit, HN).
   - Announcements from the last date to today: date, what, url, **delivery: shipped | announced**. Mark an undated one "(no date)".
   - **Only what's shipped counts.** A "y" in the matrix is for what's usable today (docs, GA in the changelog, on the pricing page, actually testable). "Coming soon," a waitlist, invite-only beta, press/blog only → "d". "d" cells don't count toward "widespread among rivals"; `diff` counts a "d → y" transition as the real launch.
   - Update the rival file to match the template (`templates/rival.md`: the feature matrix uses the product's own rows from `pm/matrix.json`, `Status`, why the announcement matters, "Position relative to us"); list which matrix cells changed.
   - The rival's homepage's top claims, at most 5, with the matrix step number ("Featured on the landing page" section); `frontyard` uses these for "the rival spotlights this, we have it, it's not on our page".
   - The rows the owner cares most about come first; every row ties back to "how much of this do we already have ready."
   - Hand verification to a separate, cheap agent (`nosy-auditor` in the plugin, haiku): the template, the evidence, and the "(unverified)" rule.
   - **If a sub-agent can't be spawned** (a non-Claude agent): research the rivals yourself, in sequence, with the same instructions; start from the oldest "Latest major announcement," at most 5 rivals per session, tell the owner the rest are "up next." If there's no web search, skip this step and say so.
3. Handle the noise: customer/award/funding news goes in a "movement" section, product features go in the matrix. In the "rivals this week" box, list what shipped and what was announced separately; don't say "we need to do this now" for something only announced — look again once it ships.
4. **Matrix proposals are proposals**. The agents write every proposed cell change to `pm/state/matrix-proposals.json` (`{ "proposals": [ { "rival", "step", "from", "to", "removal", "evidence": [ { "url", "grade": primary | secondary | marketing | gated, "page_opened", "date", "date_kind": release | page | none } ] } ] }`), not to `matrix.json`. Then `nosy matrix-proposals check` (`skill/tools/matrix-proposals.mjs`) sorts them and writes `pm/state/matrix-proposals.checked.json`: **apply** (a page was opened, and one primary item or two secondary items from different sites), **hold** (weaker, or no page opened: stays a proposal, the code unchanged; marketing-only and gated-only evidence is capped at p), **reject** (lowers a y or p to u or n without `removal: true`, since no evidence is not evidence of absence, or rests on a page date as a ship date). It warns when one url backs two rows or more (look again before applying) and when a rival or step isn't in the matrix. Hand the checked file to the refuter the way `psst` does (`nosy-refuter` reads it). Delete from `pm/state/matrix-proposals.json` every proposal it refutes: `apply` reads that file again, not the checked one. Then `nosy matrix-proposals apply` (`--dry-run` first): it writes only the "apply" class into `matrix.json` after copying it to `pm/.backup/`, re-dates (`verified_at`) every cell whose rival's pages were opened this round, and never changes a held or rejected code; `nosy matrix-proposals undo` puts the matrix back. `build-matrix` rebuilds `matrix.json` from the tables in `pm/rivals/*.md`, so `apply` writes the same cell into the rival's table too (its code, and `[verified: date]` at the end of the evidence cell, which a rebuild reads back as `verified_at`) and `undo` restores the tables with the matrix. Agents must therefore leave a rival table's code column as it is until the check said apply: a code written straight into the table skips the check. A rival that has no release-notes page at all can't be proven current or stale: say "no source to verify against", not "no change". A cell nobody could verify this round keeps its code. A proposal whose `from` no longer matches the matrix is held ("the matrix changed since the agent looked"): re-propose against the current matrix; a second `apply` of the same file changes nothing. If a new feature keeps coming up across rivals, suggest a new row (ask the owner, don't add it yourself).
5. Write the page's "rivals this week" box; then `tea`.

**Growth signals** (did a rival grow?). After `watch`, run `node <skill>/tools/rival-signals.mjs run pm` (`nosy rival-signals run`). It reads public counters only, once each, for every rival that has `sources.json` `rivals.<slug>.signals` (`github: "owner/repo"`, `npm`, `appStore`, `careers: { greenhouse | lever | ashby: "<name>" }` or `{ page: "<url>" }`; `nosy rival-signals init` proposes the block from the rival files and writes nothing): GitHub stars, forks, releases and commits in the last 30 days, weekly npm downloads, the App Store rating of the current version, open roles. Each is compared with the oldest reading from the last 28 days and saved to `pm/history/rival-signals.jsonl` and `pm/state/rival-signals.json`; the first run has no change to show ("first reading"). Tell the owner in product words: who grew, who is hiring, who shipped more, **with the number and the date it is compared with** ("Acme: 1,234 GitHub stars, +134 since 5 Sep"). These are public proxies, not revenue or users: say "interest", not "growth in revenue", and a source that couldn't be read (rate limited, no JobPosting data on a careers page) is named, never counted as zero. A founder's public post, a funding round or a hire you read yourself goes in with `nosy rival-signals note <slug> "<text>" --source <url>` (an address is required: no source, no note); notes stay on this machine and are never published. Nosy never reads LinkedIn or anything behind a login.

**neighbors discover** (finding rivals to add, not researching known ones). Candidates come from what is already here: `references/` and rival-shaped folders in the repo (a competitor's docs, a screenshot folder, a vendored comparison), the category named in `product.md`, and web search ("alternatives to", "vs" pages). Show at most 4 at a time, each with a one-line reason and its source, and research nothing until the owner confirms. Every confirmed rival gets a tier (A deep, B watch only, C reference) written to `sources.json` `rivals.<slug>.tier`, so the next plan knows what to do with it.
