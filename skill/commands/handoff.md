# handoff

Goal: an item on the team's list becomes work on GitHub, where the team already works. Nosy hosts no board and no task list: the issue, its assignee and its project card are GitHub's, and `handoff --review`, `shipped`, `ship-notes`, `roadmap` and `board-status` read them back. Only with the owner's yes does anything get written.

1. Run `node <skill>/tools/handoff.mjs pm` (or `nosy handoff`). It lists psst's final list (`pm/state/lowhanging.filtered.json`), numbered, with a suggested owner and whether the item is already on GitHub. No list yet: run `psst` first.
2. Ask the owner which item (or take the one they named). Then run `nosy handoff <#>` for the preview: the issue title and body, the assignees, the project card and its fields, and who can read the issue (a public repo: everyone, so read the text as something you are publishing). **It writes nothing.** Add `--agent` when the owner wants a coding agent on it (the free label path; see 4), `--to <login>` to pick the person, `--project <n>` for a card (or set `handoff.project` in `sources.json`), `--horizon Now|Next|Later` to set the board's Horizon field (the same field `nosy roadmap` reads with `roadmap.project.field`, so a card moved on the board moves the roadmap).
2b. **Board and card fields.** A card carries what the owner would otherwise have to ask: `Status`, `Horizon` (Now / Next / Later, the field `nosy roadmap` reads), `Signal` (the kind of signal that put the item on the list), `Asked for` (a count, only when the item has one), and, with `--area <number or name>`, `Area` and `Rivals with it` (how many rivals have that matrix area). Only fields the board really has are set; the preview lists the ones it lacks ("Not on the board"). **`--area` is the owner's to name:** show the matrix areas (`pm/matrix.json`, `steps`), ask which one this work closes, and never pick one from the title yourself. No board yet, or a board with fields missing: `nosy handoff --setup-board` previews what it would create (the project, linked to the repo, and the fields); `--yes` creates it, after the owner has seen the preview. Which field a board view uses for its columns can only be set in GitHub's own UI; tell the owner that in one line.
3. **Who:** the suggestion is the login that wrote most of the recent commits on the item's evidence file, and only when that login can be assigned in the repo. It is a suggestion: say so, say the receipt ("3 of the last 4 commits on that file") and let the owner change it. An item with no code evidence has no suggestion; ask the owner. Never pick from names, titles or guesswork.
4. **Agent:** a person stays accountable, the agent is delegated. `--agent` is the free path: the issue gets the label `agent-ready` and, with `handoff.agentMention` in `sources.json` (for example `@claude`), one line mentioning it; the owner's own agent or workflow picks it up. `--agent copilot` assigns GitHub's Copilot coding agent, **which is paid** (one premium request and Actions minutes of the owner's plan per session, billed to them past the allowance): use it only when the owner asks for Copilot by name, say the cost before `--yes`, and if the preview says Copilot isn't assignable, don't look for a way around it. Never pick Copilot because it happens to be available. Tell the owner which happened, in those words; don't say an agent "was assigned" when only a label was set.
5. **Write the body yourself when the item deserves it.** The tool's own body is short on purpose (why now, where to look, the owner suggestion). For an item the owner is going to hand to someone, read the code at the evidence path, write the problem, a short plan and **Done when** criteria that can be checked, save it to a file and pass `--body-file <file>`. Nosy adds the marker line. Keep customers' names and quotes out (a count is fine); the privacy scan stops on personal data and secrets.
6. **Read the preview to the owner before `--yes`**: the title, who is assigned (and why), agent or label, card. `nosy handoff <#> --yes` then writes in this order and stops at the first failure: the label (if needed), the issue (or the edit of the issue the item already is), the agent, the card and its fields. A project card needs the `project` scope; it is checked first, and `gh auth refresh -s project` fixes it (the owner runs it, not you).
6b. **What became of it:** `nosy handoff --review` reads every handed-off issue back (open or closed, its card's Status, the merged pull request that closed it) and prints PROPOSALS, writing nothing to GitHub or to the matrix: the matrix cell the work may now close (only when `--area` was given at hand-off; it is the owner's to change, and only after checking it works; "merged" is not "works"), and whether `nosy ship-notes` will tell whoever asked. A closed issue with no merged pull request gets no proposal: ask whether it was fixed. `nosy shipped` shows the merged part of it on its own (`--review --brief`). Run `--review` before a weekly look, and after a release. The week itself goes on the board with `nosy board-status` (the `roadmap` command, step 11).
7. It never closes, deletes or rewrites an issue, never opens a second one for the same item (`pm/state/handoff.json` plus an exact-title check), never pushes. Say the issue URL back.

Config, optional, in `sources.json`: `handoff: { project: { owner, number, type, status, horizon }, agentLabel: "agent-ready", agentMention: "@claude" }`.
