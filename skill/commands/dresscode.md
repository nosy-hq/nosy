# dresscode

Goal: score the product's design system (the house's dress code) across 20 areas with evidence, try whether an AI can apply it without guessing, and turn the 3–5 gaps that matter **now** into a plan. So the product manager speaks the same language as the designer: which decision is written down, which is missing, which measurement lives where.

Not a code review. It doesn't look at screen code, style, or bugs; it looks at the design system's **decisions** (goal, principle, scope, component maturity, governance).

The area list is inspired by designsystems.surf's "AI-ready Design System Roadmap" (4 stages × 5 areas). The checklist items, evidence rules, AI trial, and roadmap tie-in are Nosy's own.

1. Score it: `node <skill>/tools/dresscode.mjs pm`. The script finds the design system with `read-design.mjs` (from the repo, `pm/sources.json`; it guesses the root from anchor files like DESIGN.md, design-tokens.json, docs/design-system/, a UI registry) and writes:
   - `pm/state/design.json`: the reader model (roles, goals, principles, scope, components and their maturity, tokens, AI scenarios, broken references). `canwe` and `spill` read this.
   - `pm/state/dresscode.json`: the state of the 20 areas (ready · partial · missing · ask), each check's evidence (file:line), the plan. If there was a previous run, it shows what changed area by area.
   - `pm/design/<date>.md`: the report.
   If the root is guessed wrong, write `"design": { "root": "apps/web" }` to `sources.json`. If the design system lives only in an Artifact (not in the repo), this is an agent step — the script itself can't reach the Artifact tool and stays offline: use the Artifact tool's `read` action (`path`/`paths` for the design system's published files, or `list` with `scope: "files"` first to see what's there) to save the files into a local folder (e.g. `project/`), then run dresscode against that folder with `--folder <path>` (or `--from-artifact <path>`, the same thing under a clearer name for this case) and add `--artifact-url <url>` so the report records where the files came from. In folder mode, tests and the changelog aren't visible — say so in the report.
2. Verify the evidence (two passes; every run). The script matches words and headings, it doesn't know meaning: "Feedback" could be a UI pattern, "A person approves" could be a product principle. So every line-based ✓ starts as a ✓? (unverified) and is written as a candidate to `pm/state/dresscode-verify.json` (an instruction plus each candidate's ±5 lines).
   - If there are candidates, hand a haiku sub-agent only this file: it applies the `instruction` in the file and writes its answer as `[{key, decision: yes|no, reason}]` to `pm/state/dresscode-verdicts.json`. Then run `node <skill>/tools/dresscode.mjs pm decision pm/state/dresscode-verdicts.json` and re-run dresscode. A rejected match is skipped and the check looks at the next candidate; keep going while new candidates turn up. Each check tries **at most 3 candidates** (counted from the rejections on record for that check id, tunable with `sources.json` → `threshold.dresscodeMaxCandidates`); past that, no new candidate is proposed and the check shows ✗ with "N candidates rejected — owner can add evidence with `add <id> <file:line>`" — at that point it's the owner's call, not another round. Verdicts are stored in `pm/design/approvals.json` with the check + file + line-window summary: as long as the text hasn't changed, the same match isn't asked again, and a line shifting doesn't invalidate the verdict. Every rejection (judge's or owner's) is also written to `pm/learned.json` as a `learn reject --type dresscode` record (the bridge to the paragraph below), so `learn list`/`remove`/`--duration` manage it like any other rejection.
   - **No sub-agent** (agents that can't spawn one): judge the candidates yourself, but only from `dresscode-verify.json`'s instruction and each candidate's ±5 lines, without reading the rest of the repo first, and write the same `[{key, decision, reason}]` file.
   - **✗ lines:** the document might exist under another name, elsewhere (`git grep`). If you find it, show the owner; if the owner confirms, `node <skill>/tools/dresscode.mjs pm add <id> <file:line> --reason "..."` (the id is next to each check in the report, e.g. `Goals#2`). If the design system is in a different root, fix `sources.json`'s `design.root`.
   - **If the owner disagrees with a verdict:** `node <skill>/tools/dresscode.mjs pm accept|reject <id> <file:line> --reason "<owner's sentence>"`. The owner's verdict overrides the agent's; the agent can never override the owner's.
   - **? (ask) lines:** ownership, communication, measurement, feedback can't be seen from the repo. Ask the owner once (AskUserQuestion, at most 4 questions); write the answer to `pm/decisions.md` in the owner's own words. An "ask" status closes once the decision is written to the repo (the governance doc).
   - **Broken reference:** if a document mentions a file that doesn't exist, an agent will search for it, fail to find it, and guess. This is the cheapest fix — put it at the top of the plan.
   - **A stubborn false positive that isn't worth an exception pattern:** `node <skill>/tools/learn.mjs pm reject "<matching text>" --context "<check id or area, e.g. Design–Code Alignment#3>" --type dresscode --reason "..."` — the same `learn reject` command `measure-size` and `canwe` already use. dresscode reads it back the same way it reads its own exception patterns (shown in the report as "eliminated by pattern … (learn)"); manage it with `learn list`/`remove`/`--duration` like any other learned rule. Every judge/owner rejection already writes one of these automatically (the "N candidates rejected" note above), so this is mainly for a false positive found by hand, outside the two-pass flow.
   - **Don't ask the same wrong thing twice (the exception pattern):** if there was a rejected match, `node <skill>/tools/dresscode.mjs pm suggest [--pm <another product's pm> ...]`. For each rejection, the script suggests a short phrase around the triggering word ("server catalog", "what is announced"); the phrase never crosses a sentence/cell boundary, never starts with a filler word, and never eliminates evidence accepted in any product. Show the list to the owner:
     - For this product only: `suggest --sec <id,...> --apply` (only exceptions drawn from this product's own rejections get written, to `pm/design/approvals.json` → `exception`).
     - For every product (Nosy itself, `skill/data/dresscode-exceptions.json`): `suggest --publish`. Without a selection, only a pattern seen in **≥2 products** is written — a pattern seen in one product hasn't proven it's general; if the owner decides it is anyway, spread it deliberately with `--sec`. No product text gets written into Nosy; only the pattern, the general reason, and how many products it was seen in. Add a `reason` sentence to the file; a commit into the Nosy repo needs the owner's approval.
     Generalizing: if the same trigger word was rejected multiple times in the same check with different neighbors ("server catalog", "MCP catalog", "tool catalog"), the suggestion becomes one pattern (`(?:MCP|server|tool) catalog`) and replaces the narrower patterns in the same scope. Only observed neighbors go in (not `"\w+ catalog"`); a neighbor that matches a protected line ("component catalog") is left out. A generalization of a pattern already spread in Nosy gets spread with `--publish` without a selection (the family was pre-approved). If a single-word neighbor matches a protected line, a two-word precursor is tried instead ("API catalog" can be evidence, "public API catalog" can't). Trigger matching tolerates suffixes and the target language's own inflection, and uses that language's letter boundary. The pattern's structure (side, root, neighbors) is stored in the record as `structure`.
     A line matched by a pattern never reaches the judge; it shows up in the report as "eliminated by pattern … (product | Nosy)."
   - In the chat summary, give the "Evidence: N verified · N pending · N rejected" line; don't present an area with a remaining ✓? as "ready."
3. AI readiness trial (at most 2 areas, cheap model): actually try whether the agent applies the design system without guessing it. **No sub-agent: skip this step and say so in the report** ("AI readiness trial not run: no fresh-context agent"). Run in your own context it proves nothing, because you have already read the design system; never simulate it or fill in a result. Pick the area from the plan or the product's nearest upcoming screen work (`pm/waves.md`). Give a haiku sub-agent **only** the role files from `pm/state/design.json` (repo path + ref; no other context) and a real task:

   | Area | Task (fill in with a real roadmap item) | Trustworthy answer |
   |---|---|---|
   | Goals | "Which serves the design system's goals more, work item <A> or <B>?" | Names the written goal; says if there isn't one |
   | Principles | "Decision A or decision B? Decide using the principles." | Shows the winning principle in order; doesn't invent a new rule |
   | Scope | "Is <request> inside the design system's scope: included, deferred, excluded?" | Shows the row from the scope table; doesn't widen scope |
   | Components | "What parts would you build <screen> from?" | Uses only recorded components; flags a missing part as "not there, needs a decision" |
   | Content | "What does <screen>'s empty, loading and error state say?" | Quotes the content guide's formula |
   | Deprecation | "What replaces <old part>, which screens are affected?" | States the recorded `replacement`; says it doesn't know if it doesn't |

   Append to every trial's instruction: "Cite your source with file:line, in backticks (e.g. `Table`), for every component/token name you use. Flag missing context; don't make things up." Score the answer with three questions: did it cite a source · did it flag a gap · did it invent a component, token or rule that isn't on record. The third question doesn't have to be graded by eye: save the sub-agent's raw answer to a file and run `node <skill>/tools/ai-note.mjs pm <answer-file>` — it reads `pm/state/design.json`'s component/token names (the same "on record" the eyeballed grading used), pulls every backtick- or JSX-tag-named identifier out of the answer, and marks each ✓ (on record) · "did you mean X?" (edit distance ≤2 or same stem — likely a typo or rename, not invention) · ✗ (not on record, nowhere close: invented). Deterministic, no model call; exits 1 if anything is invented. Fold its verdict into the trial's invention question instead of eyeballing the component list. Result: `pm/design/<date>-ai.md`, with ai-note's summary line (N on record · N close · N invented) alongside the three-question grade. If the product has its own `ai-readiness` result table, **don't write into it** (the never-write-externally rule); put the suggested line in the report instead.
4. Write the plan: the script's chosen 3–5 gaps come with "why now" (Define-stage gaps, decisions the product manager is waiting on, and gaps slowing down roadmap screen work rise to the top). Per line: area, why now, smallest next step, owner (suggestion), review date. Don't make a full backlog; keep it a focused plan. If the owner approves, the gaps go into `scoop` (design-system work is roadmap work too) and `tea`'s page gets a one-line summary.
5. Short chat summary: "N ready · N partial · N missing · N to ask," the most important gap right now and why, the AI trial's result. The report's **Talking to the designer** section (principles in order, component maturity, measurements) is the product manager's meeting notes for the designer — show it too, if asked.
6. Next command: if the top gap needs a decision, `spill <area>` (e.g. `spill "design system scope"`); if screen work is waiting, `canwe "<screen>"` will now also show the ready parts in the design system.

How often: when the design system changes, or once a month. It's not part of `stakeout`'s weekly cycle.
