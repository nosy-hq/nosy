# roadmap

Goal: the roadmap lives where the team already works, in the repo. Nosy builds Now / Next / Later from the evidence, from what the team already curates on GitHub, or from both, and proposes it as a pull request that edits one block of `ROADMAP.md`. Merging is the approval, reverting is the undo, and nobody opens a new tool.

1. Run `node <skill>/tools/roadmap.mjs pm` (or `nosy roadmap`). It reads `pm/state/waves.json` (run `scoop` first; not needed with `source: "github"`), writes the block to `pm/state/roadmap.md` and the same content for a dashboard to `pm/state/roadmap.json` (`{ type, generated, path, sections: { now, next, later, shipped }, hidden }`; items are `{ title, ref, url }`, shipped ones add `date`), and prints the block. Nothing leaves the machine.
2. **What goes in:** the titles as the owner wrote them (a title the writer cut mid-sentence ends at its last whole word with "…"), `(#N)` as a link when an item's reference is an issue number, and, under "Shipped recently", merged PR titles from the last 30 days (release tags when no PR merged). An item appears once, in the earliest of Now, Next, Later. Each section is capped (`max`) and ends with "…and N more" when cut. **What never goes in:** the reason text, evidence paths, scores, effort, names, customer counts, decision references (`K12`, `§3`). The privacy scan runs over the block and the JSON; a finding stops it (exit 2) and nothing is written.
3. **Read the block to the owner before offering a PR.** Titles can be internal shorthand; the owner fixes the title at its source (or skips it with `roadmap.skip` in `sources.json`) and runs again. Say what is in Now, Next and Later in the owner's language, product words first.
4. **No `origin` remote** (a repo that is exported rather than pushed): `nosy roadmap --write ROADMAP.md` puts the block into that file in the working tree (no git, no network, nothing committed); the owner reads it and commits it. The file must stay inside the repo.
5. `nosy roadmap --check` says whether `ROADMAP.md` on the integration branch is current (exit 2: behind or no block yet).
6. **The PR needs the owner's yes** (it pushes a branch and opens a pull request in their repo). With it: `nosy roadmap --pr --yes`. It works in a throwaway worktree off `origin/<integration branch>`, so the owner's checkout and uncommitted work are never touched; it changes only the block between `<!-- nosy:roadmap -->` and `<!-- /nosy:roadmap -->`, keeps every other line as written, and opens the PR with `gh`. The body lists what was added, moved and removed. If a Nosy roadmap PR is already open (head branch `nosy/roadmap-*`), it is **updated**, not duplicated: the branch becomes one commit on the current base, pushed with `--force-with-lease`, and it says "Updated <url>". If the block is already on the base branch and an old PR is open, it says that PR is now empty and leaves closing it to the owner (Nosy never closes a PR). No `origin` remote: it says so and the preview stays in `pm/state/roadmap.md`.
7. **Language:** the block's headings and sentences come from `skill/data/lang/<code>/roadmap.json` (en, tr): `--lang`, else `sources.json` `language`, else English. An unknown language is English with one line on stderr. The marker comments stay English.
8. Config, all optional, in `sources.json`: `roadmap: { path: "ROADMAP.md", now: ["Now", "When code lands"], next: ["Needs backend", "After"], later: ["Open requests"], shipped: { days: 30, max: 10 }, skip: ["title fragment"], max: { now: 8, next: 10, later: 10 } }`.
9. **GitHub as the source** (read-only; no issue, milestone or project is ever written), `roadmap.source`: `"evidence"` (default), `"github"` (only what the team curated there) or `"both"` (a curated item decides its own section; the evidence's copy of the same item is dropped). Inputs, each optional: `labels: { now: "roadmap:now", next: "roadmap:next", later: "roadmap:later" }` (open issues with the label); `milestones: true` (open milestones by due date: soonest = Now, the next = Next, the rest and the undated = Later, with their open issues); `project: { owner: "acme", number: 3, type: "organization" | "user", status: { now: ["In progress"], next: ["Todo", "Ready"], later: ["Backlog"] } }` (a Projects v2 board, by its `Status` field, up to 300 items; closed, archived, redacted and other-private-repo items stay off). If `gh` can't read a source (no `read:project` scope: run `gh auth refresh -s read:project`; not found; offline) it says exactly that on stderr and the block is built from the evidence only; the PR body carries the same note. Tell the owner when that happens.
10. **Scheduled:** the Action's `roadmap: "true"` input runs `roadmap --pr --yes` after the weekly loop when `sources.json` has a `roadmap` key, with the job's own token (permissions `contents: write`, `pull-requests: write`; the repo setting that lets Actions create pull requests) and prints the PR URL in the job summary. It updates the open PR each week instead of opening another. A Projects v2 board needs a token with `read:project`, which the job's own token usually lacks: use labels or milestones there, or run it locally.

Never edit `ROADMAP.md` by hand inside the block, never push without `--yes`, never close a roadmap PR, never put a reason, a person or a customer into a title yourself.
